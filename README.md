# EPUB Proofreader — Phase 5（PDF追従）

日本語OCR EPUBを、縦書き・ルビを保持して原本PDFと照合するWebアプリです。AIは修正候補を提示し、**承認した修正だけ**を本文へ反映します。元EPUBは保持されます。


Dockerで始める場合は [起動・保存・移行の手順](docs/DOCKER.md) を参照してください。

## プロジェクトと発行版

EPUBを読み込むたびに「ファイル名＋読み込み日時」で新しいプロジェクトを作成します。PDFは任意です。「プロジェクト一覧」から切り替え、明示的に削除するまで原本・作業本文・PDF・編集履歴・AI結果を保持します。既存DBの日時不明のデータは「読み込み日時不明」と表示します。

「EPUB発行」でv1、v2…と版を追加し、そのEPUBをプロジェクト内に保存します。EPUBのOPFに独自名前空間の版番号と発行情報を記録します。EPUB規格の`package version="3.0"`は変更しません。再ダウンロードでは版は増えません。発行済みEPUBを再アップロードした場合、その版番号を引き継ぎます。

普段の作業は自動保存されるため、手動のバックアップ操作は不要です。移行用の「作業データを書き出す（.eproof）」は、上部の「操作」メニュー内にあります。元EPUB、作業本文、PDF、Undo／Redo、確認状態、表示位置、未保存入力、AI候補・判断履歴・ジョブの記録を含みます。読み込みは別プロジェクトを作成します。AIジョブは記録として復元し、自動送信しません。検査を続ける場合は改めてジョブを開始してください。APIキー・エンジン登録・過去の発行EPUBそのものは.eproofに含めません。**すべてのプロジェクトと発行版・エンジン・実行途中のジョブを丸ごと保存するには、データフォルダーと別管理の暗号化キーをバックアップしてください。**

## 起動

Python 3.12以上とuvを使用します。GitHubのソースから起動する場合は、先にfrontendでpnpm install --frozen-lockfileとpnpm buildを実行します。Dockerでは自動でビルドします。

```sh
uv sync --locked
uv run uvicorn epub_proofreader.app:app --app-dir backend --host 127.0.0.1 --port 8000 --workers 1 --timeout-graceful-shutdown 5
```

[アプリを開く](http://127.0.0.1:8000/)。終了はCtrl+C。ブラウザを閉じてもバックエンドを停止しなければAI処理は続きます。Macで確認済み。Debian用Docker設定を同梱しますが、コンテナ起動とWindows実機は未検証です。

## いつもの校正

1. 「新規プロジェクト」でEPUB（必須）とPDF（任意）を選択します。保存済みの作業は「プロジェクト一覧」から開きます。
2. 02／本文で章・表示ページ・文字サイズを選択し、03／校正の「前へ／次へ」で段落・文を移動します。300文字以上の段落は文単位へ自動切替します。
3. 03には「現在の内容」と常時入力できる「編集内容」を並べます。AI推奨の訂正があれば入力欄に表示し、差分のある文字だけ、原文側・編集側の両方で赤字になります。「更新」で確定します。ルビは「ルビの訂正」で章の一覧ウィンドウを開きます。段落挿入・分割・結合は折りたたみ内にあります。
4. 文字レイヤーのあるPDFは、選択した本文にページが自動追従します。原本PDFとの対応ページ・矩形も手動で登録できます。
5. Undo／Redo、確認状態、検索・置換、編集履歴、入力の保護は引き続き利用できます。
6. 「EPUB発行」で構造検証後に版を保存・ダウンロードします。

複雑なルビは構造を保護します。本文欄でルビ親文字を直接書き換えず、ルビ編集ウィンドウの親文字・読み欄を使ってください。EPUB出力は元XHTMLの編集結果を使用し、プレビューHTMLから作り直しません。

## AIエンジンの設定

03の「AI検査・結果一覧」を開き、「エンジン管理」で、新規登録・編集・削除・接続テスト・モデル取得・デフォルト設定ができます。同じサーバーの別モデルを複数登録できます。過去の校正結果はエンジン削除後も残ります。途中のジョブがあるエンジンを削除する場合は、先にジョブを中止してください。

初期設定は`config/initial-engines.json`です。初回のDB作成時にだけ登録し、その後は画面で変更します。

| プロバイダー | 接続先 | 設定 |
|---|---|---|
| Ollama | `http://localhost:11434` | 初期モデル `qwen3:14b`。モデル一覧を取得して切替可能 |
| Google Gemini | `https://generativelanguage.googleapis.com` | APIキーとモデル名 |
| Anthropic Claude | `https://api.anthropic.com` | APIキーとモデル名 |
| OpenAI | `https://api.openai.com` | APIキーとモデル名 |

別のOllama接続先は管理者が`AI_ALLOWED_ORIGINS`（カンマ区切りの起点URL）で許可します。`http://localhost:11434`と`http://127.0.0.1:11434`も初期許可済みです。Docker内のlocalhostはコンテナ自身を指します。TailscaleへはDockerホスト／コンテナから到達できるネットワーク設定が必要です。

### APIキー

Ollamaには不要です。クラウドAPIキーを保存する前に暗号化キーを準備します。

```sh
python3 scripts/configure_local.py
# ローカルでは secrets/ai_secret_key を自動で読み込みます。
# 別の場所の鍵を使う場合：
# export AI_SECRET_KEY_FILE="/absolute/path/to/ai_secret_key"
```

既存のキーを上書きしないでください。ファイルは通常のデータフォルダーの外に置き、紛失しないよう別にバックアップします。`AI_SECRET_KEY`環境変数で渡すこともできます。サーバーを起動し、管理画面のAPIキー欄へ登録します。暗号化してSQLiteに保存し、ブラウザへ再表示しません。空欄で保存すると既存キーを維持します。キーを更新する場合は新しい値を入力します。ブラウザからクラウドへ直接通信しません。

## AI校正の流れ

1. エンジンと「現在の段落／現在の章／書籍全体」を選択します。**アップロードだけでは実行しません。**
2. 「AI校正開始」。クラウドでは送信する範囲、概算料金、上限を確認してから開始します。本文と前後の文脈を送る検査、親文字と読みの対応を送る検査を別々に実行します。ルビがない範囲では本文検査だけを行います。PDF画像は送信しません。
3. 段落ごとに結果と進捗をSQLiteへ保存し、画面に随時表示します。ブラウザを閉じても処理は継続します。閲覧・手動編集も並行できます。結果の受信でカーソル・段落を勝手に移動しません。
4. 「前／次のAI検知」は候補単位で移動し、該当本文をハイライトします。「未確認のみ／未確認＋保留／すべて」を切り替えられます。同じ段落の複数候補も個別に移動します。
5. 「結果一覧」は状態・カテゴリ・エンジン・章で絞り込めます。位置をクリックして本文へ戻れます。
6. 本文の訂正内容は常設の入力欄、ルビは別ウィンドウで確認して「更新」します。「確認済みにする」は原文を変更せず、AIの指摘を許容した判断として記録します。修正案がない場合もこの操作ができます。更新だけが編集を発生させ、既存の履歴とUndo／Redoへ記録されます。却下・保留は結果一覧で操作できます。AI検査後に対象段落の本文・ルビが変わっていたら承認を拒否します。再検査または手動編集で確認してください。

修正案の生成は必須ではありません。AIが対象の文を指定できれば、具体的な修正が分からない場合も要確認として保存します。修正案の原文が照合できない場合は、その案を適用可能にせず文全体の確認へ切り替えます。

AIはOCR復元を目的とし、旧字・歴史的仮名遣い・方言を保つよう指示しています。ただし誤提案や見落としはあります。**AI自己評価は正確な確率ではありません。原本と照合して判断してください。**

### 長時間処理と中断

バックエンド内の単一ワーカーで処理します。段落を処理し終えた時点で一時停止し、中止後は未確定の結果を登録しません。失敗した段落を再試行できます。接続等の失敗が5段落に達すると一時停止します。JSONや対象範囲が不正なAI応答は、具体的な検証理由を渡して最大3回試行します。不正な候補が混在していても、安全に照合できた候補は保持します。段落は要再検査としてエラーに記録するため、見落としを「完了」として隠しません。OllamaのThinkingはOFFです。

バックエンド再起動後は、途中のジョブを「再開待ち」にし、手動で再開します。完了した段落・候補は保持します。未完了の段落のAPI呼び出しは再実行されることがあり、その分の料金が発生し得ます。APIへの送信とDB保存を外部サービスをまたいで厳密に一回だけ行う保証はありません。

### クラウドの料金

エンジンごとに入力／出力100万トークン当たりのUSD単価を入力します。価格はコードに固定しません。未設定なら「推定不能」と表示します。利用上限を使う場合は両単価が必要です。

ルビのある範囲は本文・ルビの2回問い合わせるため、開始前の概算に両方を含めます。各呼び出し前に概算と残額を確認し、超過が予想される場合は停止します。利用量が返らず金額が不明になった場合も、上限付きジョブは次の呼び出しを止めます。料金上限で止まった場合、画面で上限を増やして再開できます。再試行分も使用量へ集計します。課金事業者の実際の請求上限を設定する機能ではなく、単価の誤設定、追加料金、トークン見積もり差までは保証できません。クラウド側の利用上限も併用してください。

## データの永続化とDocker

[Debian・Dockerの起動と移行](docs/DOCKER.md) · [GitHub公開準備](docs/GITHUB.md)

保存先は`DATA_DIR`、未設定なら`EPROOF_DATA_DIR`、どちらも未設定ならアプリ内`.data`です。SQLiteに原本・PDF・編集・発行版・エンジン・暗号化済みAPIキー・AIジョブ・結果・判断・使用量を保存します。サーバー停止後にフォルダーをバックアップするか、SQLiteのbackup APIを使ってください。暗号化キーは別管理です。削除後の空き領域はSQLiteが再利用するため、DBファイルのサイズが直ちに縮むとは限りません。

```sh
# 新規環境のみ。既存DBを移す場合は元の暗号化キーを復元してください。
python3 scripts/init_docker.py
docker compose up --build -d
```

`./data`を`/app/data`へbind mountし、秘密キーを`/run/secrets/ai_secret_key`に別マウントします。ポートはホストの127.0.0.1に限定します。コンテナを再作成しても同じdataと秘密キーを使えば復元できます。削除したり別フォルダーに変更すると既存データを利用できません。

DockerにはJavaとチェックサム検証済みのEPUBCheck 5.4.0を同梱します。Docker以外の通常起動では以下を実行し、`JAVA_BIN`（任意）と`EPUBCHECK_JAR`を指定できます。

```sh
uv run python scripts/install_epubcheck.py
export EPUBCHECK_JAR="$PWD/.tools/epubcheck-5.4.0/epubcheck.jar"
```

EPUBCheck未導入時は「利用不可」と表示し、内部構造検証で発行します。EPUBCheckが利用でき、検証に失敗した場合は発行しません。DockerでJARを保持する場合は`.tools`も別途マウントし、`EPUBCHECK_JAR`を指定してください。

## 制約と将来の対応

- ローカルの単一ユーザー用です。認証は未実装。信頼できない利用者へ公開しないでください。所有者列と共有エンジン用ACLテーブルを用意していますが、ログイン・共有ユーザーの管理は将来対応です。
- 許可した起点URLへの接続のみ行い、転送先へ追従しません。将来の公開運用には認証・実際の共有認可・DNS再解決対策・ネットワーク制御を追加する必要があります。
- 複数AIの同時実行・結果比較はPhase 5向けです。別エンジンで順番に検査した結果は保持します。
- iPad向けの読書表示・PDF切替・編集画面を実装しています。オフライン運用は未対応です。
- 複雑ルビ、新規ルビ追加、複雑組版・元CSSそのままの再現には制約があります。構造変更は隣接p要素が中心です。
- EPUB64 MiB、PDF256 MiB、.eproof512 MiB、編集欄2万文字まで。長いAI対象はルビ範囲をまたがず分割します。XMLの通常読み込みを先に試し、文字参照エラーが出た場合に限って既知の縦中横タグ混入を復元します。不正な実体や復元不能なXMLは拒否します。
- AI品質はモデルに依存します。25万文字の全書籍実運用・性能測定とクラウド実接続は未検証です。

## EPUBの表示方向

章ごとに、EPUB内のCSS・インライン指定から縦書き／横書きを判定します。標準のwriting-mode、-epub-writing-mode、-webkit-writing-mode、ローカルCSSの@import、セレクターの優先順位と!importantを扱います。指定がなければCSS標準どおり横書きです。綴じ方向rtlだけで縦書きとは判定しません。外部CSSは取得しません。

ページ送りの左右はプロジェクト全体で固定します。EPUBの綴じ方向rtlでは左が次、ltrでは右が次です。指定がなければ文字量の最も多い章の縦横で決め、扉・奥付など別の表示方向の章でも入れ替えません。横書きは上下方向、縦書きは横方向へページを送り、校正対象へ追従します。文字サイズは02の「表示設定」にあります。

プレビューの章全体を一つの表示方向に揃えます。章内で縦横が混在する複雑な組版、表示幅条件のあるメディアクエリ、@supports等の高度なCSSは完全再現していません。EPUBの原本・出力用XHTMLは表示処理で変更しません。

既存段落を分ける操作は「既存の段落を二つに分ける」、欠落本文の追加は「欠けた本文を段落として追加」と区別しています。本文差分は手入力にも追従します。極端に大きい全面置換では処理時間を制限し、共通の前後部分を除いた変更範囲を赤字にします。

## XMLエラー時だけの自動修復

通常の厳密なXML読み込みで文字参照エラーが出た時だけ、jisui2epubの縦中横タグが数値文字参照を分断した既知の形式を復元します。例：`&#<span class="tcy">x</span><span class="tcy">27</span>;` → `&#x27;`。修復後も厳密なXML検証を行い、別のエラーが残る場合は読み込みを中止します。XMLのrecoverモードや本文の推測補完は使用しません。

画面上部に件数を通知し、展開すると対象ファイル・行番号・修復前後を確認できます。原本とそのハッシュは保持し、編集・Undo・発行には修復済みの作業用データを使います。元のEPUBをダウンロードすると読み込み時のバイト列をそのまま返します。発行EPUBには修復を含みます。作業データの書き出し／復元でも原本と修復状態を保持します。修復は本文校正とは別の読み込み記録で、Undoによって破損XMLへ戻しません。

属性、コメント、CDATA等の中は修復しません。未知のタグ混入、復元不能な文字参照、XMLで禁止された文字、DTD・実体の問題、ZIP構造の問題は従来どおりエラーです。

## iPadでの利用（0.4.5）

iPad等のタッチ端末、または画面幅1100px以下では読書表示を基本にします。本文／PDFを切り替え、「編集」で校正画面、「読書に戻る」で本文へ戻ります。通常の3ペイン表示へは「通常表示」、PCから読書表示へは「読書表示」で切り替えられます。この表示方式の選択は端末のブラウザ内に保存し、MacとiPadで別々に利用できます。

本文をクリック・タップすると校正対象を選択します。iPadの読書表示では、その段落・文の編集画面を直接開きます。300字以上の段落では文単位です。前へ／次へは選択位置を基準に移動します。読書時のルビタップだけで編集ウィンドウが開くことはありません。PDFのページ位置・本文の表示位置・編集中の入力は既存の保存機能を利用します。

### 接続

Macで通常のサーバーを終了してから、`start-ipad.command` をダブルクリックします。同じ仮想環境を利用します。あるいは次を実行します。

```sh
.venv/bin/python scripts/serve_ipad.py
# アドレスを選ぶ場合（Macに割り当てられたWi-Fi／TailscaleのIPv4）
.venv/bin/python scripts/serve_ipad.py --host 192.168.1.10
```

表示されたURLをiPadのSafariで開きます。Wi-Fiのアドレスなら同じLAN、100.64.x.x等のTailscaleアドレスなら同じTailscaleネットワークから接続します。端末のファイアウォールが接続確認を表示する場合は、この利用範囲で許可してください。

単一のアプリプロセスでlocalhostと選択したプライベートIPv4だけに接続を受け付けます。全インターフェースには公開しません。認証のない個人用ツールなので、信頼できるLAN／自分のTailscale内で使います。MacとiPadで同じデータを利用しますが、同一プロジェクトの同時編集は避け、競合表示が出た場合は再読み込みしてください。Mac側サーバーは起動したまま使います。

縦横回転、タップしやすいボタン、セーフエリア、ソフトウェアキーボード、PDFの指でのスクロールに対応したレイアウトです。iPad Safari実機での最終確認は別途必要です。オフライン化・端末への全書籍保存・ネイティブアプリ化は含みません。

## 未確認AI指摘とルビ一覧（0.4.6）

未確認・保留・Undo済みの本文AI指摘は02／本文で赤字表示します。確認済み・承認済み・却下済みの指摘は赤字から外します。原文変更で位置が照合できない古い候補は誤った場所を赤くせず、結果一覧で再検査を促します。ルビの読みは本文検知の赤字対象に含めません。古いブラウザで文字範囲の強調APIがない場合は段落単位の赤字になります。

「前のAI検知」「次のAI検知」は本文対象だけを移動します。ルビの指摘は「ルビの訂正」の章別一覧にまとめ、未確認の項目を赤字にします。各項目で親文字・読みを変更でき、「左へ広げる／左を戻す／右へ広げる／右を戻す」で隣接本文との境界を調整します。範囲を選んでから親文字を訂正してください。「更新」はその項目を確定し、「確認済みにする」は本文・ルビを変更せず指摘を許容した判断を記録します。

範囲変更は元の親文字と重なる範囲に限り、隣接する平文だけを取り込み／戻します。複雑なルビ、空白の配置が複雑なルビ、装飾要素や別のルビをまたぐ範囲変更は保護します。本文の順序とルビの要素構造を保持し、Undo／Redo・書き出し・作業データの復元に対応します。未保存入力は項目ごとに保護します。

## 文字付きPDFへの追従とiPadのページ送り

PDFの既存の文字レイヤーをブラウザ内で検索し、選択した段落・文に対応するページへ移動します。章の切り替え、本文のクリック、03の前へ／次へ、AI検知への移動、02のページ送りから追従します。文字の準備中もPDFは手動で移動できます。索引は同じブラウザのセッション中に再利用し、再読み込み後は作り直します。

編集後は、本文の一部、修正前の本文、前後の文、章内の対応箇所を手掛かりに位置を探します。縦書きOCRの文字順や小さなルビ文字も考慮します。前後の文や章から近くのページを選ぶ場合は「推定」と表示します。候補が曖昧な場合は無理に移動しません。「本文に追従」を外すと自動移動を停止し、その設定はプロジェクトに保存します。

画像だけのPDFや利用できる文字がないPDFには自動照合を行いません。OCRの追加処理やPDF画像のAI解析は行わず、PDFを外部AIへ送信しません。確認・修正の判断は人間が行います。

iPadの読書表示では、本文・PDFの左右に大きめの三角ボタンを配置します。縦書き本文は左が次、右が前、横書き本文とPDFは左が前、右が次です。HTTPのLAN／Tailscale接続でも、AI校正開始とEPUB発行の操作IDを生成できるようにしています。

### 読書画面の移動とPDF拡大

本文のページ送りは章をまたぎます。次章には最初のページ、前章には最後のページへ移動します。縦書きでは本文・PDFとも左が次、右が前です。横書きでは右が次、左が前です。iPadのPDFは2本指で拡大縮小、1本指で移動できます。本文をタップして開いた校正で「更新」「確認済みにする」が成功すると、読書画面へ戻ります。通常表示では校正画面を維持します。

### ローカルのJava

Mac標準の`/usr/bin/java`は実体のない案内コマンドの場合があります。Java 11以上を`-version`で確認してから使用します。`.tools/java/bin/java`に実行環境があれば優先し、次に`JAVA_HOME`、PATH、Macのインストール済みJavaを探します。明示した`JAVA_BIN`が不正な場合は別のJavaへ勝手に切り替えません。DockerにはJavaを同梱します。

### まとめ検査（0.5.2）

章・書籍全体の新規ジョブは、最大4段落をエンジン設定の文字量以内でまとめて送ります。章の境界を越えず、長い段落は分割し、ルビは1回40件以内に区切ります。本文とルビは別の問い合わせのままです。AIは異常が疑われる箇所だけを返し、問題のない段落は列挙しません。段落ID・文ID／ルビ番号と原文をサーバーで照合します。候補がない段落も処理済みとして数え、不正な応答は再試行・要再検査として記録します。旧ジョブは保存された1段落方式で再開します。料金概算はまとめ送りの問い合わせ数に基づきます。一時停止は処理中のまとまりが終わった時点で反映します。

### iPhone向け操作

タイトル行をコンパクトにし、副題を省略しました。プロジェクト名・作成日時・最新版は1行に表示します。新規プロジェクト、一覧、Undo／Redo、検索・置換、履歴、作業データ書き出し、EPUB発行は上部の「操作」にまとめています。画面下は保存状態のみです。狭い画面の校正欄は現在の内容・編集内容を縦に並べます。

### 最小候補応答（0.5.3）

AIに理由・分類・確信度を要求せず、本文は段落ID・文ID・文内の開始文字位置（0始まり）・元の文字列・任意の修正候補だけを返す。文字位置が不明ならnull。位置と元の文字列をサーバー側で照合し、不一致・重複で特定不能なら修正案を適用せず文全体を要確認にする。ルビは別の問い合わせで、段落ID・ルビ番号・任意の親文字／読みの修正候補のみ。異常なしは空配列。理由の表示はツール側の共通文言で、分類は本文の要確認／ルビ。新しい候補の確信度表示は省略する。過去の候補や従来形式の応答は引き続き読み込める。

OpenAIのgpt-6-luna（同モデルの日時付きIDを含む）にはreasoning.effort=noneを明示。他のモデルには送らない。参考：[モデル仕様](https://developers.openai.com/api/docs/models/gpt-6-luna)。実際の速度・検出品質の比較は未実施。入力の最大4段落・合計1200文字、既存の再試行方式は今回変更していない。

### AI検出結果のクリア（0.5.4）

03/校正の「AI検査・結果一覧」に「AI検出結果をクリア」を追加。現在のプロジェクトに保存した本文・ルビの全AI候補を非表示にし、赤字・候補数・候補移動にも反映する。承認済みの本文修正、検査履歴、使用量・料金は保持。「クリアした結果を戻す」で非表示の候補をまとめて復元でき、再起動や作業データの書き出し／読み込み後も復元可能。AI実行中はクリア不可（一時停止・中止後に操作）。一時停止中のジョブの状態は変えず、再開後や新しい検査で得た結果は通常どおり表示する。クリア前の結果を復元すると、新しい結果と併せて表示される。

### AIへの指示の編集（0.5.5）

03/校正の「AI検査・結果一覧」→「AIへの指示を編集」で、共通・本文・ルビの指示を別々に編集できる。「デフォルトに戻す」は初期値を入力欄へ戻し、「保存」で適用する。未保存で閉じる場合は破棄確認。全プロジェクト・全AI共通でライブラリDBに保存し、再起動後も保持。各欄6000文字まで。別画面での更新競合を検知する。位置・JSON形式などの通信上の指示はツール側で付加する。

本文の初期値は口語・文学表現・倒置・省略・反復・ひらがな表記を許容し、文字の置換や削除で説明できるOCR異常を主な検出対象とする。多くは一文字～少数文字の異常だが、柱などの混入は長くても対象とする。単なる文章改善や漢字への変換は提案しない。ルビには本文の一文字条件を適用しない。意味の近い当て字・文学的な独自ルビを許容し、日本語の語・活用形として成立しない読みを探す。固有名詞・外来語・方言・擬音語・造語・複数語は未知というだけで誤り扱いせず、判断できない場合は報告を控える。

保存後に開始する検査へ適用する。新しいジョブは開始時の指示を保存し、設定変更後に再開してもその指示を使う。既存候補は再判定しない。見積もりには編集済み指示の文字量も含む。作業データにはジョブ開始時の指示も保存するが、取り込みによって全体設定を上書きしない。

### XHTML単位の作業保存（0.5.6）

編集・ルビ修正・段落操作・Undo/RedoではEPUBを組み立てない。保存済みのEPUBを基準として保持し、変更したXHTMLだけをライブラリDBのediting_filesへ保存する。通常の追加編集では基準EPUBのBLOBも書き直さない。元のEPUB・既存の作業用EPUB・履歴は移行時に置き換えず、そのまま基準として読み込む。全Undo時は取り込み時の内容へ戻し、差分を除去する。

解析済みの書籍データを再利用し、変更したXHTMLの章だけをXML検証・段落/文/ルビの再計算にかける。キャッシュしたXMLを直接書き換えず、編集対象のツリーを複製する。キャッシュがなくなった場合は、保存した基準EPUBとXHTML差分から再開できる。XML宣言・DOCTYPE・処理命令も保持する。

EPUBの組み立てと全体検証は、EPUB発行、EPUB書き出し、作業バックアップや履歴の書き出し時に行う。既存の.eproof形式を維持し、作業用EPUBはその時点で組み立てて含める。発行時のEPUBCheckは従来どおり。画面には引き続き全章の概要を返し、表示中の章のHTMLを再取得するため、通信・画面の再配置時間は残る。

独立コピー（1,867段落・27章）で文字編集2回を比較：保存APIは従来0.47〜0.48秒、変更後約0.07秒。章プレビュー取得は従来0.13〜0.19秒、変更後約0.003秒。編集時のZIP組み立ては2回から0回。ローカルでキャッシュが利用できる条件の参考値で、ブラウザー描画やネットワークの待ち時間は含まない。

### 校正完了後の確認済み・自動移動（0.5.7）

03/校正の「更新」「確認済みにする」は、対象段落（見出しも可）の人間確認済み状態を保存する。「確認済みにする」はAI候補がない箇所でも使える。更新した本文とAI候補の承認／確認を保存してから、確認状態と入力途中データの整理を保存する。

通常表示では、最新のAI検出結果を取得し、現在の候補より後にある本文の未確認候補へ進む。確認済み・承認済み・却下・ルビ・本文更新で位置が古くなった候補は自動移動から除外する。候補を直接選んでいない場合は確認した段落／文より後から探す。末尾では先頭へ戻らず、その場に留まる。02/本文は対象範囲を表示し、01/PDFは本文追従を有効にして登録済みページまたは利用可能な文字レイヤーから追従する。画像のみのPDFで対応ページの登録がない場合は従来どおり手動移動。PDFの照合にはAI検知を含む文を優先し、段落編集モードでも文単位で検索する。

読書表示からの編集では自動的に次の候補へ進まず、元の読書位置へ戻る。保存・確認に失敗した場合は進まない。既存の検出結果は一括確認にせず、操作した候補だけを承認／確認する。同じ段落の他の有効な未確認候補は引き続き対象とする。
